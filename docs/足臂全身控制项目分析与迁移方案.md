# 一、三个项目的总体定位

## 1.1 一句话对比

## 1.2 最重要的判断

- 不建议把 Deep-Whole-Body-Control 整个 Isaac Gym 环境和 rsl_rl 原样搬进 `legged_wbc_mjlab`。

- 更合理的分工是：

    - 从 Go2_ARX_mjlab 借用 mjlab 任务组织方式和 MuJoCo 语义；

    - 从 Deep-WBC 借用统一策略的训练思想：分支动作、分解奖励、Advantage Mixing、history adaptation 和 domain randomization；

    - 从 `legged_wbc_mjlab` 现有代码借用 HIM 的现代 TensorDict/ONNX 接口、事件/传感器管理、部署 FSM 和地形场景；

    - 根据 Piper 的关节、坐标系、执行器、质量和力矩限制重新建立动作与奖励标定。

- 不能直接复用源项目 checkpoint。ARX L5 与 WidowX 250s 与 Piper 的机械臂关节范围、零位、连杆质量、轴方向、末端坐标系、安装高度和执行器都不同；即使都是“12 腿 + 6 臂”，策略输入语义也不相同。

# 二、Go2_ARX_mjlab：在 mjlab 中实现的足臂统一控制

## 2.1 项目目标和设计边界

- `Go2_ARX_mjlab` 的 README 明确把项目定位为：在 mjlab 中增加 Unitree Go2 + ARX L5，并提供“底盘速度跟踪”和“末端位姿跟踪”任务。

- 注册的两个任务是：

    - `Mjlab-Velocity-Flat-Go2arm`；

    - `Mjlab-Velocity-Rough-Go2arm`。

- 策略的高层输入是两种 command：

    - `base_velocity`：期望底盘线速度和 yaw 角速度；

    - `ee_pose`：期望机械臂末端位姿，位置为机身坐标系下的 `(x, y, z)`，姿态为 `(qw, qx, qy, qz)`。

- 策略的动作是两个 manager action 的拼接：

    - `joint_pos`：12 个 Go2 腿关节位置目标残差；

    - `arm_pose`：6 个 ARX L5 关节位置目标残差。

- 这条路线的关键工程选择是：不让策略输出末端笛卡尔速度或力矩，也不在每一步强制求 IK；统一策略直接输出所有关节的 position target，MJCF 中的 position actuator/PD 负责跟踪。

## 2.2 机器人模型和执行器

主要文件是：

```text
Go2_ARX_mjlab/src/mjlab/asset_zoo/robots/go2arm/go2_arm_constants.py
Go2_ARX_mjlab/src/mjlab/asset_zoo/robots/go2arm/xmls/go2arm.xml
```

- MJCF 将 Go2 的 `base` 与 ARX L5 的 `base_link` 刚性连接，安装位姿在 XML 注释中给出：相对于 Go2 trunk 大约是 `xyz = (0.085, 0, 0.094)`。

- 腿部为 12 个关节：

    - `FR_hip_joint`, `FR_thigh_joint`, `FR_calf_joint`；

    - `FL_hip_joint`, `FL_thigh_joint`, `FL_calf_joint`；

    - `RR_hip_joint`, `RR_thigh_joint`, `RR_calf_joint`；

    - `RL_hip_joint`, `RL_thigh_joint`, `RL_calf_joint`。

- 手臂为 `joint1` 到 `joint6`，夹爪的 `joint7`/`joint8` 存在于模型中，但不属于策略 action。末端 site 名称为 `end_effector`。

- `go2_arm_constants.py` 使用 `XmlActuatorCfg`，通过 `command_field="position"` 把腿和臂的 MJCF position actuator 暴露为关节位置目标接口。

- 默认位置：

    - 根部位置约为 `(0, 0, 0.35)`；

    - 腿部使用 Go2Arm_Lab 风格的站立姿态：髋关节左右符号相反，前腿 thigh 约 `0.8`，后腿 thigh 约 `1.0`，calf 约 `-1.5`；

    - ARX L5 初始关节约为 `(0, 1.55, 0.95, 0.45, 0, 0)`；

    - 夹爪初始为 `joint7=0.044`、`joint8=-0.044`，但夹爪动作不进入 policy。

- 动作缩放：

    - 腿部三个关节族均为 `0.25 rad` 的残差尺度；

    - 手臂为 `(0.5, 0.7, 0.7, 0.7, 0.5, 0.5) rad`；

    - 真实执行时是 `target = default_joint + scale * normalized_action`，再由 position actuator 施加力矩。

- 这与 Deep-WBC 的源代码数值不同。迁移到 Piper 时，必须使用 Piper 自己的 `control.stiffness`、`damping`、`effort_limit`、关节 range 和 action scale，不能只把 ARX 的比例复制过去。

## 2.3 观测结构和历史布局

`src/mjlab/tasks/velocity/config/go2arm/env_cfgs.py` 中的 actor observation term 顺序是：

1. `base_ang_vel`：机身角速度；
2. `joint_pos`：18 个关节相对默认位置；
3. `joint_vel`：18 个关节相对默认速度；
4. `actions`：上一时刻 18 维动作；
5. `velocity_commands`：3 维底盘速度命令；
6. `go2_pose_command`：7 维末端位置/姿态命令；
7. `projected_gravity`：机身坐标系下的重力投影。

- 每个 term 设置 `history_length=10`，因此每个历史 term 是“该 term 自己的 10 帧”，而不是把 10 帧先按完整 frame 拼接。

- 单帧宽度是 `3 + 18 + 18 + 18 + 3 + 7 + 3 = 70`，actor 输入为 `10 * 70 = 700`。

- native sim2sim 脚本特别强调了这一点：`mjlab` 的 manager 会按 term 保存历史并在 term 维度拼接。部署时如果改成“frame-major 的 10 帧完整帧拼接”，虽然维度仍为 700，但每个特征的位置都会错误，策略会失效。

- critic 使用 actor terms 加上 privileged terms：

    - base 质量；

    - 末端/子树质量；

    - 关节执行器力矩；

    - base 线速度；

    - 脚部接触事件。

- 这说明 Go2_ARX_mjlab 已经具备 asymmetric actor-critic 的基本模式：actor 只看可部署观测，critic 可以使用仿真特权信息。但它没有实现 Deep-WBC 那种单独的 privileged encoder + history adaptation，也没有双优势训练。

## 2.4 末端位姿 command 的生成

`UniformPoseCommand` 的设计是 Go2_ARX_mjlab 最值得迁移的部分之一。

- 位置 command 在机身/机械臂基座附近定义，内部使用 `(x, y, z)` 和四元数。

- 采样范围大致为：

    - `x: 0.4 ~ 0.6 m`；

    - `y: -0.35 ~ 0.35 m`；

    - 世界高度 `z: 0.1 ~ 0.55 m`；

    - roll 固定为 0；pitch/yaw 在约 ±20° 内采样。

- 初期范围更窄，例如 x 约 `0.45 ~ 0.5`、y 约 ±0.05、z 约 `0.35 ~ 0.4`，随后通过 `curriculum_coeff` 和 `num_steps_per_env` 线性扩大到最终范围。

- 采样的姿态不是完全独立的随机姿态：pitch 与“从机械臂基座指向目标的位置向量”相关，yaw 也与目标水平投影方向相关，再叠加小范围随机扰动。这样生成的末端姿态更像“朝向目标”，不会产生大量无意义或不可达的姿态。

- `position_command_error_exp` 将 body-frame command 转到 world frame，与末端 site 的 world position 做 L1 型误差；`orientation_command_error` 用四元数误差幅值。

- 迁移到 Piper 时应保留“command frame”和“末端 site”的显式定义。Piper XML 中末端 body 名为 `end_effector`，安装在 `Piper` body 下；其根 body、机械臂安装高度和轴向与 ARX L5 不同，不能照搬 ARX 的世界/机身转换。

## 2.5 奖励设计

Go2_ARX_mjlab 在 `env_cfgs.py` 中将足臂奖励直接放在同一个 reward dictionary 中，典型项如下。

### 末端任务

- `end_effector_position_tracking`：位置跟踪指数奖励，权重 `0.8`，标准差 `0.2`；

- `end_effector_orientation_tracking`：姿态误差项，权重为负值；

- `end_effector_action_rate`：只惩罚 arm action 的相邻变化；

- `end_effector_action_smoothness`：只惩罚 arm action 的平滑性。

### 底盘任务

- `tracking_lin_vel_x_l1`：前向线速度跟踪，权重 `3.0`；

- `track_ang_vel_z_exp`：yaw 角速度跟踪，权重 `2.0`；

- `lin_vel_z_l2`、`ang_vel_xy_l2`：抑制不期望的垂向和横滚/俯仰角速度；

- `feet_air_time`、`foot_contact`：鼓励合理步态和支撑接触；

- `hip_deviation`、`joint_deviation`：保持腿部关节在合理姿态附近；

- `height_reward`、`flat_orientation_l2`：控制机身高度和水平姿态。

### 接触和安全

- base/arm 与 terrain 接触会触发 `base_arm_ground_contact`；

- thigh/hip 等腿体与 terrain 接触会触发 `leg_body_ground_contact`；

- rough terrain 模式下还保留 terrain generator 的边界终止；

- flat terrain 模式用约 70° 的 `bad_orientation` 作为摔倒终止。

- 与 Deep-WBC 相比，这套奖励更细、更像通用 locomotion MDP；Deep-WBC 论文的核心实验反而使用了更简单的“跟踪 + 能量 + 存活”奖励。迁移时建议先采用 Go2_ARX 的可解释安全项，再逐步加入 Advantage Mixing，而不是一开始同时重写所有 reward。

## 2.6 接触传感器和 rough terrain

- Go2 MJCF 没有每只脚的 site，因此项目用 body/geom 匹配的 ContactSensor：

    - calf 与 terrain 的 contact force 用于脚部接触、air time 和接触奖励；

    - base、base_link、link1~link8 与 terrain 的接触单独监测；

    - hip/thigh 与 terrain 的接触单独监测；

    - base 子树内部的 self collision 有独立 sensor。

- rough task 在 `go2arm_rough_env_cfg` 中启用 MuJoCo CCD、增大 contact match 上限，并把脚的摩擦拆成 slide/spin/roll 三轴随机化。

- terrain 来自 mjlab 的 `ROUGH_TERRAINS_CFG`，支持平地、金字塔台阶、反向台阶、随机网格、heightfield 等 primitive/heightfield 组合，并使用 terrain level curriculum。

- flat task 复用 rough 配置再切换到 plane，移除 terrain scan/self collision 等不必要传感器，并保留独立的摔倒终止。

## 2.7 训练和部署链路

- 训练入口：

```text
uv run train Mjlab-Velocity-Flat-Go2arm ...
uv run train Mjlab-Velocity-Rough-Go2arm ...
```

- PPO 配置使用 5 个 learning epochs、4 个 mini-batches、`gamma=0.99`、`lam=0.95`、自适应 KL，默认 actor/critic 为两层 256 维 MLP。

- 这里的 runner 是普通 `VelocityOnPolicyRunner`，不是 Deep-WBC 的定制 runner；因此没有：

    - arm/leg 两个独立 advantage；

    - value mixing；

    - privileged latent 与 history latent 的正则；

    - 独立 history encoder 的 DAgger/在线更新。

- native sim2sim：

    - 从 checkpoint 中读取 actor；

    - 使用 10 帧、每项独立 deque 的 700 维观测；

    - 每 20 ms 做一次 policy 推理，MuJoCo physics dt 为 5 ms；

    - `target_joint_pos = DEFAULT_JOINT_POS + action * ACTION_SCALE`；

    - 将 position target 写入 actuator，并可视化目标/实际末端位姿；

    - 支持终端键盘在线修改底盘速度和末端位置/姿态。

- 部署脚本是很好的“控制接口回归测试”，但不是完整真实机器人部署：README 明确说明真实部署仍在进行中。

# 三、Deep-Whole-Body-Control：论文和参考实现

## 3.1 论文要解决的问题

- 论文标题是 **Deep Whole-Body Control: Learning a Unified Policy for Manipulation and Locomotion**，CoRL 2022，作者为 Zipeng Fu、Xuxin Cheng、Deepak Pathak。

- 论文认为传统足臂系统常把问题拆成：

    - 腿部 locomotion controller/MPC；

    - 手臂 IK/operational-space controller；

    - 一个额外的规则层负责协调。

- 拆分的根本问题是腿和手臂在动力学上强耦合：

    - 腿弯曲可以扩大末端工作空间；

    - 手臂伸展会改变整机质心和支撑需求；

    - 末端目标在脚边时，单独 IK 可能不可达，但下蹲/前倾后整机可达；

    - 手臂向侧面伸出时，机身 roll 和腿部支撑会影响稳定性。

- 论文的目标不是训练“更大的两个 policy”，而是让一个统一 policy 同时产生 leg-arm synergy。

## 3.2 系统平台和论文结果

- 真实平台：Unitree Go1 + Interbotix WidowX 250s 6-DoF arm + parallel gripper。

- 计算与通信：policy/adaptation 在 Raspberry Pi 4 上 50 Hz 运行，WidowX 软件栈在 Nvidia TX2 上运行，通过 UDP 通信；夹爪开合由 joystick/script 控制，不属于 policy action。

- 传感器：RealSense D435/D435i 靠近手腕/夹爪安装，用于 AprilTag 视觉引导。

- 展示任务：擦白板、抓取杯子、按门禁按钮、放置、投掷、拥挤环境抓取、边走边完成末端轨迹。

- 论文报告的仿真趋势是：统一策略相比 separate 和 uncoordinated policy 具有更低 base acceleration、更低速度和 EE 误差，以及更高生存率；统一策略的 arm workspace 和受扰动生存率也更高。

- 论文中列出的 Regularized Online Adaptation 实验显示，正则化后的 history adaptation latent 与 privileged latent 的差距接近零量级，并在 OOD payload、COM、摩擦和电机强度下优于普通 RMA/纯 domain randomization。具体数值属于论文实验设置，不应直接当作 Piper 上的预期指标。

## 3.3 MDP 建模

论文把策略写成：

$$
\pi(a_t \mid s_t, a_{t-1}, z_t, command)
$$

其中：

- base state：roll、pitch、base angular velocity；

- arm state：6 个 arm joint 的 position 和 velocity；

- leg state：12 个腿关节 position、12 个 velocity、4 个脚接触指标；

- previous action：18 维；

- EE command：位置和姿态；

- locomotion command：前向速度和 yaw 角速度；

- environment extrinsics latent：20 维。

动作写成：

$$
a_t = [a_t^{leg}, a_t^{arm}],\quad a_t^{leg}\in\mathbb{R}^{12},\quad a_t^{arm}\in\mathbb{R}^{6}
$$

底层统一使用 joint-space position control。

### 一个需要特别注意的维度差异

- 论文正文把当前状态写成约 75 维，但仓库实现的 `WidowGo1RoughCfg.env.num_proprio` 是：

$$
2 + 3 + 20 + 20 + 18 + 4 + 3 + 3 + 3 = 76
$$

- 这 76 维对应：

    - base roll/pitch 2；

    - base angular velocity 3；

    - 20 个 DOF position；

    - 20 个 DOF velocity；

    - 18 维上一动作；

    - 4 个脚接触；

    - 3 维底盘 command；

    - 3 维当前 EE spherical command；

    - 3 维 EE orientation Euler command。

- 这里的 20 个 DOF 是 18 个 policy DOF 加上 2 个 gripper DOF；夹爪动作置零，但观测仍包含状态维度。

- 迁移时不能依据论文正文的 75 维猜测输入，必须以最终 Piper XML、task observation manager 和导出模型的实际 shape 为准。

## 3.4 Reward：两套可分解的回报

论文把总 reward 分成 manipulation reward 和 locomotion reward：

$$
r_t = r_t^{manip} + r_t^{loco}
$$

论文表格中的典型形式是：

$$
r^{manip} = 0.5\exp\left(-\left\|[p,o]-[p^{cmd},o^{cmd}]\right\|_1\right)
-0.004\sum_{j\in arm}|\tau_j\dot q_j|
$$

$$
r^{loco} = -0.5|v_x-v_x^{cmd}|
+0.15\exp\left(-|\omega_{yaw}-\omega_{yaw}^{cmd}|\right)
-0.00005\sum_{i\in leg}|\tau_i\dot q_i|
+0.2+0.5v_x^{cmd}
$$

参考实现的 config 更细一些：

- locomotion 侧启用了 `tracking_lin_vel_x_l1=0.5`、`tracking_ang_vel_yaw_exp=0.15`、`energy_square=-6e-5`、`survive=0.2` 等；

- manipulation 侧启用了 `tracking_ee_sphere=0.55`、`arm_energy_abs_sum=-0.004` 等；

- `compute_reward()` 分别得到 `rew_buf` 和 `arm_rew_buf`，然后一起返回给 PPO。

- 这套“奖励分支化”是 Advantage Mixing 的前提。单纯把所有 reward 加成一个标量后再按 action slice 训练，无法复现论文的 credit assignment 机制。

## 3.5 EE command：球坐标、插值和可达性

- EE 位置用球坐标 `(l, p, y)`：半径、pitch、yaw。

- 球坐标原点固定在 arm base 附近，高度基准用常数 `z_invariant_offset=0.53`，不随机身高度、roll、pitch 改变。这样 EE command 的语义不会因为机器人暂时下蹲或倾斜而漂移。

- 每个目标不是瞬间跳变，而是从当前 command 到新目标在 `T_traj` 内线性插值，然后再保持一段 hold time。

- 参考 config 的训练范围大致是：

    - `v_x^{cmd}: 0 ~ 0.9 m/s`；

    - `ω_yaw^{cmd}: -1 ~ 1 rad/s`；

    - `l: 0.2 ~ 0.7 m`；

    - `p: -2π/5 ~ 2π/5`；

    - `y: -3π/5 ~ 3π/5`；

    - trajectory time `1 ~ 3 s`。

- `collision_check()` 对球坐标轨迹采样 10 个中间点，拒绝穿过预设碰撞区域或地下限制的目标轨迹。注意它主要约束 command 轨迹，不是一个完整的实时几何碰撞规划器。

- 对 Piper 迁移时，建议保留“球坐标 + 插值 + command 轨迹检查”的思想，但重新根据 Piper 的安装位置、link geometry 和实际 workspace 估计碰撞盒；ARX/WidowX 的上下限不能直接使用。

## 3.7 双头 actor-critic

`rsl_rl/modules/actor_critic.py` 的结构是：

- privileged encoder：`24 -> 64 -> 20`，输出环境 extrinsics latent；

- history encoder：输入 10 帧 `10 x 76`，用线性层和 1D convolution 输出同样宽度的 latent；

- actor 当前帧 `76` 与 latent `20` 拼接后进入 backbone；

- backbone 后分成两个 action head：

    - `actor_leg_control_head`：输出 12 维并接 `tanh`；

    - `actor_arm_control_head`：输出 6 维并接 `tanh`；

- critic 同样分成两个 value head，输出 `[V_loco, V_manip]`，而不是一个标量 value。

- `get_actions_log_prob()` 把 Gaussian log probability 按腿和臂分别求和，得到两个 log-prob 分量；entropy 也分成腿/臂两项。

- 原实现可选 adaptive arm gains：arm head 输出 6 个 position action 加 6 个 gain residual，训练时用它们重建 arm torque，并可做 torque supervision。默认 `adaptive_arm_gains=False`，所以第一版迁移不需要实现这一项。

## 3.8 Advantage Mixing：论文核心技巧

### 为什么需要它

- 如果一开始对所有 action 使用同一个总 advantage，策略会发现“保持腿不动、只追踪末端”是更容易的局部最优：腿部探索会让 base 晃动，base 晃动又会让 EE error 变大。

- 结果是 manipulation 学会了，locomotion 不学；或者 locomotion 学会了，arm 变成扰动项。

### 数学形式

设 PPO rollout 中有两类 advantage：

- `A_manip`：由 manipulation reward 计算；

- `A_loco`：由 locomotion reward 计算。

论文的 policy objective 可以理解为：

$$
J = \mathbb{E}\left[
\log\pi(a^{arm}|s)(A_{manip}+\beta A_{loco})
+\log\pi(a^{leg}|s)(A_{loco}+\beta A_{manip})
\right]
$$

其中：

$$
\beta(t)=\min\left(\frac{t}{T_{mix}},1\right)
$$

- β=0 时：arm 主要由 manipulation advantage 更新，leg 主要由 locomotion advantage 更新；

- β 从 0 增加到 1 后：arm 和 leg 都逐步承担对方任务的贡献，全身协同被训练出来。

### 参考实现的实际写法

`PPO.update()` 中先得到 `advantages[..., 0/1]`，然后：

```text
mixed[0] = advantage[0] + beta * advantage[1]
mixed[1] = advantage[1] + beta * advantage[0]
```

再与两个 action log-prob 相乘。需要注意：代码的第 0/1 维命名取决于 `rew_buf` 的拼接顺序，迁移时必须在 storage、reward、critic head、log_prob head 四处保持同一约定，不能只改一个公式。

### 源项目的训练 schedule

- `mixing_schedule=[1.0, 0, 3000]`：β 从训练初期开始，约 3000 次更新线性升到 1；

- 论文 supplementary 的大规模训练约为 10000 iterations、5000 environments、每环境 40 steps，约 2 billion samples；

- 仓库当前 config 使用 24 steps、4 mini-batches、5 epochs、learning rate `2e-4`，属于参考实现参数。

## 3.9 Regularized Online Adaptation

### 要解决的 sim-to-real 问题

- 仿真 teacher 可以直接看到 payload、质量、COM、摩擦、电机强度等真实部署不可见的 environment extrinsics；

- 真实 student 只能从最近一段本体观测和动作历史中推断这些变化；

- 传统两阶段 RMA 的 teacher 可能学到 history student 根本无法恢复的 latent，形成 realizability gap。

### 两个 latent

- privileged information encoder `μ(e)`：

$$
z^{\mu}=\mu(e)
$$

其中 e 是仿真可见的环境参数。

- adaptation module `ϕ(history)`：

$$
z^{\phi}=\phi(s_{t-10:t-1},a_{t-11:t-2})
$$

它只看最近历史，部署时可运行。

### 损失

$$
L = -J(\pi,\mu)
+ \lambda\left\|z^{\mu}-sg[z^{\phi}]\right\|_2^2
+ \left\|sg[z^{\mu}]-z^{\phi}\right\|_2^2
$$

其中 `sg` 是 stop-gradient。

- policy/privileged encoder 端优化 RL objective 加第一项正则；

- adaptation module 端用第二项模仿 privileged latent；

- λ 从 0 线性增加到 1，使 teacher 不会长期跑到 student 无法实现的区域；

- 论文算法每隔 H 次 rollout 做 adaptation update，补充材料中 H=20，λ 在约 5000 iteration 后从 0 增加到 1。

### 参考实现的训练流程

1. rollout 时交替使用 `z_mu` 和 `z_phi`；
2. storage 记录 current/next observations、privileged latent、history latent；
3. PPO update 更新 actor、critic、privileged encoder；
4. history encoder 用 DAgger-like update 拟合 privileged latent；
5. 记录 `priv_reg_loss`、`hist_latent_loss`、`priv_reg_coef`。

### 迁移建议

- 不要把 Deep-WBC 的 adaptation 和当前 HIM 估计器直接混成一个模块。

- 当前 `legged_wbc_mjlab` 的 HIM 是“history -> base linear velocity + contrastive latent”，它解决的是 locomotion 的部分可观测性和速度估计；Deep-WBC adaptation 是“history -> environment extrinsics latent”，它解决的是随机动力学参数的适配。

- 第一版足臂 WBC 可以先用普通 asymmetric critic + domain randomization，不做 latent；第二版先加入 history adaptation；只有在单纯 history policy 对负载/摩擦 OOD 明显不够时，再加入 privileged latent 正则。

# 四、两个足臂项目的异同

## 4.1 共同核心

- 都使用 12 个腿关节 + 6 个机械臂关节的统一动作空间；

- 都采用 joint-space position target + 低层 PD，而不是 policy 直接输出 torque；

- 都把 base velocity command 与 end-effector command 同时提供给策略；

- 都依赖 history/privileged information 来弥补 sim-to-real 的部分可观测性；

- 都认为 arm 和 leg 的耦合是能力来源，而不是需要完全消除的扰动；

- 都使用 domain randomization、摩擦/质量/电机强度扰动、接触与跌倒约束；

- 都不把夹爪开合强行放进 18 维 policy action，夹爪由更高层脚本或 joystick 控制。

## 4.2 关键不同

| 对比项 | Go2_ARX_mjlab | Deep-WBC |
|---|---|---|
| 框架 | mjlab manager-based RL | Isaac Gym legged_gym 手写环境 |
| arm model | ARX L5 | WidowX 250s |
| observation history | 每个 term 独立 10 帧，700 维 | 当前 76 + privileged 24 + 10×76 history，总 raw 860 |
| actor/critic | 普通 MLP，普通一个 value | actor/critic 双分支，腿/臂分别输出 log-prob/value |
| reward | 一个 reward dictionary，EE 与 locomotion 项同处 | `rew_buf` 和 `arm_rew_buf` 两套回报 |
| Advantage Mixing | 没有 | 有，β 从局部 credit assignment 逐步混合到全身 |
| adaptation | asymmetric critic 的 privileged terms，但无论文式 joint adaptation | privileged encoder + history adaptation + latent regularization |
| EE command | body-frame Cartesian pose，姿态 quaternion，mjlab command manager | spherical `(l,p,y)`、轨迹插值、collision sample |
| terrain | mjlab primitive/heightfield terrain generator、terrain curriculum | Isaac Gym fractal/noise rough terrain |
| 部署 | native MuJoCo checkpoint sanity check，键盘 EE/base command | TorchScript MuJoCo deployment，真实 Pi/TX2 UDP 方案 |
| 迁移重点 | task/config/sensor/terrain | RL algorithm、storage、network、sim2real |

## 4.3 不能混淆的几个概念

- “双 action head”不等于“Advantage Mixing”：前者只是网络结构，后者还要求双 reward、双 value、双 log-prob 和训练时的 β 调度。

- “critic 看到 privileged observation”不等于“Regularized Online Adaptation”：普通 asymmetric critic 只改善 value 估计，不能让 actor 在部署时恢复仿真 extrinsics latent。

- “有 10 帧 history”不等于“history adaptation 已完成”：还需要定义 history layout、估计器目标、训练 loss、导出图和部署输入顺序。

- “输出 18 维 position target”也不等于“两个机器人可以共用策略”：关节顺序、默认角度、scale、坐标轴、力矩上限和末端 site 任何一项不一致都会破坏策略。

- 工作树中旧的 `src/tasks/deep_wbc/go2_piper` 配置和 MDP 文件被删除，说明项目正在从旧命名/旧尝试迁移到新的 `wbc` 命名；后续实现应避免继续依赖 `deep_wbc` 路径。

# 六、面向 Go2-Piper 的迁移总设计

## 6.1 推荐的最终控制架构

建议最终采用下面这条数据流：

```text
速度 command + EE pose command + 本体状态 + action history
                              |
                    统一足臂 actor
                 /                    \
       leg action head (12)      arm action head (6)
                 \                    /
          18 维 joint position residual
                              |
                Piper/Go2 position actuators
                              |
                         MuJoCo dynamics
                              |
       actor obs / critic privileged obs / adaptation target
```

- actor 输出 18 维动作：12 腿 + 6 臂；夹爪开合保留在上层 FSM/脚本。

- critic 可以看到 EE site pose/velocity、接触、质量、摩擦、电机强度等 privileged information。

- 第一阶段不强制使用 Deep-WBC 的 adaptation latent；先让统一 policy 在固定 observation contract 下学会足臂协同。

- 第二阶段再从当前 HIM 框架扩展一个“足臂动力学/环境 latent”估计器；它可以与 base velocity estimator 共用 history backbone，也可以先独立，以降低调试复杂度。

- 第三阶段才考虑 Advantage Mixing；或者更稳妥地，先实现双 reward/双 value，再加 β schedule。

## 6.2 推荐的观测契约

不要直接复制 ARX 的 70 维，也不要直接复制 HIM 的 47 维。建议先定义一个清晰的 Piper 一帧：

### 可部署 actor frame（建议初版）

| Term | 建议维度 | 说明 |
|---|---:|---|
| `base_ang_vel` | 3 | 机身坐标系角速度，来自 IMU/仿真 sensor |
| `projected_gravity` | 3 | 机身姿态/重力方向 |
| `base_velocity_command` | 3 | `(vx, vy, wz)` |
| `ee_position_command` | 3 | 机身/arm-base frame 下的目标位置，建议先 Cartesian |
| `ee_orientation_command` | 3 或 6 | 初版可用姿态误差 Euler；更稳妥可用 6D rotation representation |
| `phase` | 2 | 可选；若采用 HIM 风格 gait phase，则保留 |
| `joint_pos_rel` | 18 | Piper/Go2 所有 policy DOF 相对默认角 |
| `joint_vel` | 18 | 所有 policy DOF 速度 |
| `last_action` | 18 | 上一时刻统一动作 |
| `foot_contact` | 4 | 四脚接触；可部署性取决于真实接触估计 |

- 最小版本若不使用 phase 和 contact，是 `3+3+3+3+3+18+18+18=69` 或姿态 6D 时 72 维；

- 若使用 phase 和 foot contact，是 77 或 80 维；

- 关键不在于追求某个固定数字，而在于：每项 term 的顺序、维度、frame、scale、history layout 必须写成唯一契约并由训练/导出/部署共同使用。

### 历史建议

- 第一版建议沿用 Deep-WBC/Go2_ARX 的 10 帧，而不是直接沿用当前 HIM 的 6 帧：10 帧在 50 Hz 下覆盖 200 ms，足臂动力学延迟和动作延迟更容易从中体现。

- 如果采用当前 HIMActorModel，建议使用 frame-major、current-first：

```text
(frame_t, frame_t-1, ..., frame_t-9)
```

- 与旧 Go2_ARX 的 term-major history 不同；二者都可以，但不能混用。

- 第一版可以让 manager 直接输出 `[B, H, F]`，避免 term-major flatten 后再写 permutation；部署 ONNX 输入也使用 `[batch, H*F]` 或显式 `[batch,H,F]`，以当前 `HIMActorModel` 支持的导出路径为准。

## 6.3 推荐的动作契约

定义一个显式顺序，例如：

```text
0:  FR_hip_joint
1:  FR_thigh_joint
2:  FR_calf_joint
3:  FL_hip_joint
4:  FL_thigh_joint
5:  FL_calf_joint
6:  RR_hip_joint
7:  RR_thigh_joint
8:  RR_calf_joint
9:  RL_hip_joint
10: RL_thigh_joint
11: RL_calf_joint
12: joint1
13: joint2
14: joint3
15: joint4
16: joint5
17: joint6
```

- 这个顺序与 Go2_ARX native sim2sim 的 18 维顺序一致，也与当前部署配置常用的 FR/FL/RR/RL leg order 接近；但最终必须以 Piper task action manager 与 XML 编译后的 actuator order 做自动校验。

- 动作语义：

$$
q^{target}=q^{default}+s\odot clip(a,-1,1)
$$

- 腿和臂的 `s` 必须分开设置；推荐初始采用小 scale，逐步扩大 arm workspace，而不是一开始使用大幅动作。

- Piper XML 当前没有可用的夹爪 slide joint policy；夹爪开合继续由独立 command/FSM 控制。

## 6.4 推荐的 command 设计

### 底盘 command

- 初版使用 `(vx, vy, wz)`，范围窄一些：

    - `vx`：`0 ~ 0.4 m/s`；

    - `vy`：`-0.1 ~ 0.1 m/s`；

    - `wz`：`-0.2 ~ 0.2 rad/s`。

- locomotion 学稳后再扩到 `vx=0.8~1.0`、`vy=±0.5`、`wz=±0.5`。

### EE command

- 初版建议用 arm-base/body-frame Cartesian `(x,y,z)` + 固定姿态或小范围 orientation offset：

    - `x`：约 `0.35~0.55 m`；

    - `y`：约 `-0.25~0.25 m`；

    - `z`：根据 Piper 安装高度定义，先限定在远离地面和机身的可达区。

- 可达后再切换为 Deep-WBC 风格球坐标 command，并加入 trajectory interpolation 和中间点碰撞检查。

- command resampling 不要每一步随机跳变；建议 4~8 s 的保持时间，EE target 1~3 s 平滑插值，便于策略学到“先改变腿姿态、再移动手臂”的协同。

## 6.5 推荐的奖励分层

第一版先做两个 reward group，但可以先用普通 PPO 总和训练：

### Manipulation group

- EE position error：指数或 smooth L1；

- EE orientation error：四元数 geodesic/sixD rotation error；

- arm action rate/smoothness；

- arm torque/energy；

- self collision；

- arm/base 与 terrain 接触。

### Locomotion group

- base linear velocity tracking；

- base yaw velocity tracking；

- base z velocity、roll/pitch angular velocity；

- body orientation/upright；

- foot air time/contact/gait；

- foot clearance/slip/soft landing；

- leg torque/energy/action smoothness；

- leg/body illegal contact 和摔倒。

### 组合策略

- 初始总 reward：

$$
r=\alpha_{loco}r^{loco}+\alpha_{manip}r^{manip}
$$

- 不要同时把 EE tracking 权重、height/orientation、action smoothness、energy 全部设得很大；先保证 reward 数量级接近，再做 ablation。

- 当普通总和 PPO 能在 flat 上同时走路和追 EE 后，再打开 Advantage Mixing。

# 七、建议的分阶段迁移路线

## 阶段 0：模型和接口审计

目标：在训练前把所有“维度/顺序/坐标系”问题一次性固定。

- 检查 `go2piper.xml` 编译后的：

    - joint names/order；

    - actuator names/order/type；

    - joint range、actuator ctrl/force range；

    - root body、Piper base、end_effector site；

    - 四脚 geom/body 名称；

    - IMU sensor 和接触传感器可用性。

- 建立一份 Piper WBC contract，至少记录：

    - action joint order；

    - observation term order/dim/scale；

    - history order and length；

    - command frame；

    - default pose；

    - action scale；

    - kp/kd/effort limit；

    - export input/output shape；

    - deployment reset pose。

- 用零动作和随机动作分别检查：

    - 腿部是否能站稳；

    - Piper 是否在正确方向运动；

    - end_effector site 是否随 joint1~6 合理变化；

    - action manager 顺序是否和部署端一致。

验收标准：不训练策略也能在单环境 MuJoCo viewer 中确认 18 个动作和末端坐标都正确。

## 阶段 1：Go2-Piper flat locomotion 基线

目标：复用现有 Go2 HIM/普通 PPO 的稳定 locomotion 能力，先让带臂机器人不倒。

- 机械臂保持默认姿态或动作 scale 设为 0；

- 训练 12 腿 locomotion，critic 可以包含 arm mass/COM；

- 在 flat plane 上验证速度 tracking、姿态、足部接触、能量和摔倒；

- 再逐步允许 arm small residual，但暂时不加入 EE command reward。

验收标准：Piper 固定姿态时，Go2 locomotion 指标接近现有 Go2 baseline，机械臂不会因为附加质量导致频繁摔倒。

## 阶段 2：静态站立 + EE reaching

目标：先学会“站住并移动手臂”，暂时不要求边走边操作。

- 底盘 command 主要采样零速度/小速度；

- EE target 从近处、低姿态范围开始；

- 使用统一 18 维 actor，但将 locomotion reward 的速度项在 standing 阶段降权；

- 加入 arm/base/terrain illegal contact 和 self collision 终止/惩罚；

- 保留 body orientation、base height 和 action smoothness。

验收标准：随机 EE target 的位置误差下降，腿会出现小幅下蹲/前倾等支撑动作，而不是只动机械臂或直接倒地。

## 阶段 3：平地足臂 unified policy

目标：在 flat 上同时追踪 base velocity 和 EE pose。

- 恢复完整底盘 command；

- 加入 EE trajectory interpolation；

- actor 输出 18 维 joint target；

- critic 使用当前 frame + privileged EE pose/velocity、接触和动力学参数；

- 先使用单标量总 reward，建立最小可复现实验。

建议的对照组：

1. 只动 arm、腿部 locomotion 独立；
2. 统一输入但 reward 不耦合；
3. 统一输入 + 总 reward；
4. 统一输入 + 双 reward/Advantage Mixing。

验收标准：统一策略的 EE error、base velocity error、survival 和能量不明显劣于单任务基线，并能在近脚目标上通过身体姿态提高可达性。

## 阶段 4：实现 Advantage Mixing

目标：解决“只追手不走路”或“只走路不动手”的局部最优。

- storage 保存两类 reward、两类 value、两类 advantage；

- actor 的 leg/arm log-prob 分开计算；

- critic 输出两个 value head；

- β 从 0 线性增到 1；

- 日志至少记录：β、两类 advantage 均值/方差、leg/arm entropy、两类 value loss、两类 reward。

- 先不加入 adaptive arm gain 和 torque supervision，减少变量。

验收标准：与 no-mixing 对照时，locomotion error 和 EE error 能在训练前期同时下降；不会出现长时间“策略原地站立只追 EE”的现象。

## 阶段 5：history adaptation / HIM 扩展

目标：让策略在看不到随机质量、摩擦和电机强度时仍能工作。

- 第一版可采用 Deep-WBC 结构：privileged encoder 输出环境 latent，history encoder 模仿 privileged latent；

- 或者更贴合现有项目，扩展 `HIMEstimator` 的输出：

    - base linear velocity；

    - dynamics latent；

    - 可选 arm payload/actuator latent。

- 不要复用当前 47 维 locomotion estimator 的 target slice；Piper WBC 的 target observation 必须重新定义。

- 导出时将 normalization + history encoder + actor 合成单一 ONNX，部署端不重复归一化。

验收标准：在训练分布外的 arm payload、base COM、摩擦、电机 strength 下，history policy 与 privileged policy 的性能差距可接受，latent imitation/estimation loss 不发散。

## 阶段 6：简单 rough terrain 和 terrain curriculum

目标：从平地迁移到用户要求的“比较简单的地形”。

建议按难度排序：

1. 低幅随机 heightfield；
2. 5 cm 台阶；
3. 7 cm 台阶；
4. 10 cm 台阶；
5. 低矮离散障碍；
6. 组合地形。

- 先保留完整 terrain scan/foot height sensor 给 critic；

- actor 初期可以不看 height scan，依赖 proprio/history；若简单地形上不够，再把低维 local scan 加入 actor；

- 使用 terrain level curriculum，从 flat/低幅开始；

- rough terrain 下必须重新调整 EE target z 范围，避免末端 command 与台阶/地面产生大量非法接触；

- 站立/操作时不要过度奖励 foot air time，否则策略可能为了 locomotion 步态破坏 EE 精度；

- 加入 foot clearance、slip、soft landing 或简化版本，避免台阶上拖脚。

验收标准：每个 terrain level 的生存率、速度跟踪、EE 误差和接触统计可独立报告，不用“混合场景平均奖励”掩盖失败地形。

## 阶段 7：Piper MuJoCo sim2sim 和真实接口

目标：让训练导出的 policy 与部署链路严格闭环。

- 复用当前 `deploy/include` 的：

    - `SimConfig` 合约校验；

    - `OnnxPolicy`；

    - `MujocoBackend`；

    - FSM getup/RL/getdown；

    - terrain scene spawn；

    - ONNX metadata。

- 新建 Piper WBC 专属部署配置，不能修改 RI-4438 HIM 配置来“兼容”18 维 arm action。

- sim2sim 必须验证：

    - observation history 的顺序与训练一致；

    - ONNX 是否已包含 normalization；

    - action clip 是否与训练一致；

    - actuator kp/kd/effort 与训练一致；

    - root/Piper/end_effector frame 一致；

    - terrain spawn offset 和 reset pose 一致。

- 真实部署前再加入：电机通信、夹爪脚本、急停、限位、动作 watchdog、低速 command 限幅和 hardware-in-the-loop 检查。

# 八、迁移时最容易踩坑的地方

## 8.1 关节顺序和 frame

- Go2_ARX 使用 FR、FL、RR、RL 顺序；当前某些 target 配置使用 FL、FR、RL、RR 顺序；Isaac Gym 与 MuJoCo 的 asset order 也可能不同。

- Deep-WBC 有 `ig2raisim`、`raisim2ig`、`*_wo_gripper` 等显式重排函数，说明 action/observation order 曾经是实际问题。

- Piper 的 `joint1~6` 轴在 XML 中都写成 z 轴，再通过 body quaternion 表达机械结构；不要依据关节名字猜轴方向。

- 所有 order 都必须由名字映射，不要依赖“模型当前返回的第几个 joint”。

## 8.2 四元数 convention

- MuJoCo 使用 `[w,x,y,z]`；Isaac Gym 常见接口使用 `[x,y,z,w]`。

- Deep-WBC 的 `euler_from_quat` 明确先解包 `x,y,z,w`；Go2_ARX/native MuJoCo 使用 `wxyz`。

- 目标姿态 error、body-to-world transform、部署 bridge 需要在一个地方统一实现并测试，不能跨项目复制 quaternion 函数。

## 8.3 EE command 的 z 语义

- Go2_ARX 的 command 位置部分在 body frame，但 z command 在内部用 world target height 修正；

- Deep-WBC 使用固定 `z_invariant_offset`，让 command 不随 torso 高度漂移；

- Piper 迁移时要先决定：`ee_z` 是相对 arm base、相对机身，还是世界高度。建议 API 采用 body/arm-base relative position，内部再转换为 world metric，这样 rough terrain 下语义更稳定。

## 8.4 position actuator 与 torque actuator

- Go2_ARX XML 直接提供 position actuator；

- Go2-Piper XML 原始 actuator 节点是 motor，constants 又通过 `BuiltinPositionActuatorCfg` 构建 position controller；

- Deep-WBC Isaac Gym 环境实际在 `step()` 内手写 torque：

$$
\tau=K_p(q^{target}-q)-K_d\dot q
$$

- 如果训练环境和 sim2sim 一边用内置 position actuator、一边用手写 torque，必须确认两者的 delay、effort limit、armature 和 target semantics 等价，否则会出现明显 sim-to-sim gap。

## 8.5 action scale 和默认角

- Go2_ARX 的 ARX 默认 arm pose 与 Piper 全零默认 pose不同；

- Deep-WBC 论文 supplementary 的 arm action range 与当前代码 config 还有差异，代码中部分 arm scale 是 0；

- 迁移必须以实际训练 config 和 compiled model 为准，文献数值只作为起点。

## 8.6 reward 数量级

- Deep-WBC 参考实现把 reward buffer 除以 100；Go2_ARX/mjlab manager 奖励通常由 manager 直接按 weight 汇总；

- 如果只复制 reward weight 而忽略 dt、buffer normalization、termination reward 和 episode averaging，PPO 学习率/entropy/clip 的相对尺度会改变。

## 8.7 history layout 和 normalization

- 当前 HIM ONNX 已经把 observation normalization 嵌入导出图；部署端不能再次 normalize；

- Go2_ARX sim2sim 使用 term-major 10 帧；当前 HIM 使用 frame-major current-first 6 帧；

- 任何 history layout 变更都必须同时修改：manager observation、model permutation、export wrapper、sim2sim YAML、单元测试。

# 九、实验和消融建议

## 9.1 最小实验矩阵

| 实验 | actor | reward/critic | terrain | 目的 |
|---|---|---|---|---|

## 9.2 必须记录的指标

### 操作

- EE position error（平均、95 分位、最大）；

- EE orientation error；

- target reachable rate；

- arm action smoothness、arm energy、arm peak torque；

- self collision/ground contact rate。

### locomotion

- base velocity L1/RMSE；

- base roll/pitch、angular velocity、height；

- survival/fall rate；

- foot slip、foot clearance、landing force；

- leg energy 和总能量。

### 全身协同

- EE command 与 body pitch/roll/yaw 的相关性；

- arm payload 变化时 base COM compensation；

- arm workspace volume；

- 统一 policy 与 separate/uncoordinated 的对照；

- β、两类 advantage 和 two-head entropy 曲线。

### 部署一致性

- 训练环境、native MuJoCo、ONNX sim2sim 三者同一初始状态下的 action 差异；

- observation frame-by-frame checksum；

- actuator target/actual joint trajectory；

- reset/getup/getdown 后 history 是否正确清零和回填。

## 9.3 推荐验收门槛

这些是工程门槛，不是论文声称：

- flat 单环境零动作/随机动作无 NaN，所有 joint/actuator 映射通过校验；

- policy export 后 ONNX 输入输出 shape 与 YAML 完全一致；

- native MuJoCo 与训练 actor 在相同 observation 上的 action 最大误差小于预先设定的数值容差；

- flat 足臂统一 policy 能完成固定 EE target 和低速前进；

- 5 cm/7 cm 台阶上不因脚体接触或明显滑移快速失效；

- 负载、摩擦、电机 strength OOD 测试中，性能下降可解释且不会出现持续发散；

- 真实硬件前必须通过低速、软限位、急停和动作 watchdog 检查。

# 十、最终建议和结论

## 10.1 应该直接迁移的内容

- Go2_ARX_mjlab：

    - `UniformPoseCommand` 的 EE command manager 思路；

    - body/world pose transform 和 command debug visualization；

    - arm/leg 分组 action scale；

    - contact sensor、illegal contact、terrain generator 和 rough/flat 双 task；

    - native MuJoCo sim2sim 的输入/动作回归方法。

- Deep-WBC：

    - 18 维统一 joint position action；

    - arm/leg 两个 action head；

    - manipulation/locomotion 双 reward；

    - 双 value、双 log-prob 和 Advantage Mixing；

    - privileged encoder + history adaptation 的 realizability regularization；

    - 质量、COM、摩擦、motor strength、payload 和 push randomization；

    - 夹爪独立于 policy action 的上层控制方式。

- `legged_wbc_mjlab`：

    - mjlab 1.6 manager/task 注册体系；

    - Go2-Piper 资产和 `BuiltinPositionActuatorCfg`；

    - HIM/TensorDict/history/ONNX 生命周期；

    - deploy config contract、FSM、runtime XML 和组合 terrain scene。

## 10.2 不应该直接复制的内容

- Deep-WBC 的 Isaac Gym `WidowGo1` 环境类；

- Deep-WBC 的旧 Python 3.8/Isaac Gym 安装链路；

- ARX L5/WidowX 的 joint defaults、action scales、EE frame 和 collision bounds；

- 旧 `deploy_mujoco` 的 860 维 raw observation contract；

- 当前 RI-4438 HIM 的 282 维/12 action ONNX 合约；

- 论文中与仓库实现不完全一致的数值，尤其是 state dimension、arm action range 和 reward normalization。

## 10.3 最终路线选择

- 最短、最稳的路线是：

    1. 先完成 Go2-Piper 18 DOF 模型/动作/末端 site 审计；
    2. 先做 flat static reaching；
    3. 再做 flat unified locomotion + EE tracking；
    4. 再实现 Deep-WBC 的 Advantage Mixing；
    5. 再把当前 HIM 的 history/ONNX 能力扩展到足臂；
    6. 最后加入 5--10 cm 简单台阶、heightfield 和 terrain curriculum；
    7. 用独立 Piper sim2sim 配置接入现有 FSM/部署框架。

- 这样做的原因是：机械模型、动作契约、reward 和 terrain 同时变化时，很难判断失败来自哪里；分阶段可以把“模型错误”“策略结构错误”“训练信用分配错误”“sim-to-real 错误”“地形难度错误”拆开。

- 最终希望得到的不是一个照搬 ARX 或 WidowX 的 checkpoint，而是一套针对 Piper 资产重新标定、在 mjlab 1.6 和当前部署框架中闭环的学习型足臂 WBC：它能在末端任务和底盘任务之间共享身体状态，并在简单地形上通过腿臂协同保持稳定和可达性。
